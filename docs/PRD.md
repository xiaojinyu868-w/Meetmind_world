# EchoWorld 产品需求文档（PRD）

> 一句话：把现实世界中的每一次相遇，转化为一个可以长期存在、持续行动、与其他智能体交互的 3D 智能体，最终形成由真实关系冷启动的智能体关系网络。

## 1. 产品本质

我们做的不是 3D 游戏，也不是 AI 社交软件，而是一套基础设施：

> 将现实世界中的相遇，转化为一个持续演化的智能体关系网络。

- 一次现实相遇被封装成 **Package**（不是名片，不是聊天记录，而是完整的"认识事件"）。
- Package 生成 **Agent**，Agent 不住在列表里，而是**生活在一个世界里**：走动、访问、交谈、参加圆桌、产生新事件。
- 3D 不是包装，而是让人物、场景、关系、事件成为**可看见、可操作、可重新组织的对象**。
- 3D 的必要性（TBD-3D1 已回答，2026-08-03）：**进入对方的场域、共同面对一个课题、在空间内互动**——人与人的社交不应局限于聊天框，这三件事是聊天框形态给不了的。

## 2. 设计原则（优先级从高到低，冲突时以上位原则为准）

### P-1 严防上下文腐烂
宁可闭环小，也要完整。**一个阶段的交互场景复杂度，不得超过当前已采集上下文的量能支撑的水平。** 有什么量的上下文，就做什么样的有用且有趣的交互；上下文不够的功能不做，而不是用编造的内容填充。

### P-2 从"人脸记忆"单闭环起步
第一个闭环只有一个任务：**把人脸和相遇第一现场忠实记录下来**，并在再次相见时可靠地恢复上下文。此闭环未验证前，不扩展其他场景。

### P-3 原始事实与模型推断彻底分离
- **事实层**（照片、录音、转写、时间地点）：只增不改，永远保留原始形态。
- **推断层**（标签、兴趣、匹配建议）：可随时重算，必须携带来源、置信度与生成时间，**永远不允许回写污染事实层**。
- **视觉化生成物同样属于推断层**：AI 生成的个人场域、人物贴图等是推断的视觉化产物，必须标注为生成物、可随素材重算，不得与事实层的现场记录混淆。
- 详见 CONTEXT-AND-MEMORY.md。

### P-4 核心单位是「人物 × 事件」，不是「人物」
底层至少两层对象：**人物资料包**（相遇事件 + 原始图片/语音上下文）与**像素小人**（Agent 的可视化形态）。一个人在不同事件中的面貌是不同的 package 条目，而不是被合并成一个静态档案。

### P-5 游戏化是好的载体：程度克制，但不预设玩法限制
游戏化是这个产品非常好的载体：驱动打开率、让关系网络可观赏、让上下文可浏览、帮助现场冷启动。游戏化的**程度**要克制——服务于上下文积累与关系价值，不喧宾夺主——但**不预设玩法类型限制**：圆桌讨论、展会交谈、现场破冰游戏（合照入场、互写第一印象、你画我猜）等都可以做，不由文档预先禁止。（2026-08-03 修订：取消"只模拟本来就会发生的事情"的限制——不用莫名其妙的限制约束设计发挥。）

### P-6 MC 体素人物 + AI 生成图片贴图
每个真实的人由生成管线产出 **MC 体素（voxel）风格模型**：体素身体 + AI 根据真实照片生成的图片贴图（头部五面 + 身体 atlas），目标是"看一眼能认出是谁"；资料包中同时保留真实人脸照片与第一现场——小人负责"世界里有你"，真实脸负责"确认是你"。体素风格成本可控、生成快、无恐怖谷风险。（2026-08-03 修订：正式方向由"有脸 per-person 低多边形管线"改为体素 + 图片贴图，原方向废弃。）

### P-7 主动式增量上下文捕获
系统不只被动记录，还要主动索取增量信息。典型路径：连接真实微信场景，给用户**具体的、可执行的微信操作建议**（如"可以问 A 是否在做教育项目"），用户执行后把新上下文带回系统。

### P-8 隐私权限是产品机制，不是事后补丁
人脸、声纹、对话内容的使用边界（仅自己 / 自己 agent 可用 / 组织内 / 本人同意公开）从第一行代码起就是数据模型的一部分。详见 CONTEXT-AND-MEMORY.md#权限圈层。

## 3. 我们不在做什么（边界）

- 不是纯粹的 3D 游戏；游戏化是载体，关系价值才是核心。
- 不是 AI 宠物/陪伴产品；agent 来自真实人物与真实相遇。
- 不是人脸识别工具；识别只是输入环节。
- 不是静态通讯录/知识库；信息进入 agent 并持续行动。
- 不是纯线上陌生人匹配；从真实线下关系冷启动。
- 不是完全自治的社会模拟实验；目的是解决关系记忆、信息复用与价值连接。

## 4. 术语表

| 术语 | 定义 |
|---|---|
| **相遇事件 Encounter** | 一次现实中的认识过程，含时间、地点、场景、对话、双方行为 |
| **人物资料包 PersonPackage** | 从 Encounter 形成的结构化数据单元：人脸、声纹、身份、介绍、交流内容、兴趣需求、关系、后续事件。**产品的最基础数据单元** |
| **像素小人 / Agent** | Package 的可行动形态：MC 体素模型 + AI 生成图片贴图（P-6），在世界中移动、访问、讨论、交换授权信息、产生事件、向真人反馈 |
| **场景模块 SceneModule** | 「一个人 + 第一次认识他的场景」的组合（人物 + 展位/场景 + 上下文）；第一现场部分属事实层 |
| **场景语言** | 世界内的情境化交互约定：靠近热点出现按键提示（E/F），触发情境菜单（喝咖啡/邀请/开会）与环境播报；交互全部按键化 |
| **市集 Bazaar** | 室外主场景，一条可扩展的街：摊位/小屋是应用入口；定位"向外社交"——多人活动与因共同课题开启的陌生人互动发生于此 |
| **咖啡厅 Cafe** | 市集街上的一间室内小屋；定位"熟人社交"——两人/三人聊事、圆桌会议 |
| **场域 Field** | 由个人素材经 AI 生成的特质空间（风格化、有隐喻；**推断层的视觉化产物**，标注生成、可重算）；进入对方场域 = 与对方相处 |
| **个人关系世界 World** | 每个用户拥有的世界，生活着其认识的人的 Agent 与场景模块；由市集（室外）+ 咖啡厅等小屋（室内）+ 各人场域组成 |
| **智能体网络 Network** | 多个 Agent 交互形成的关系与价值匹配网络，产品长期最有价值的部分 |
| **世界快照 World Snapshot** | World Service 输出的世界状态序列化结果，Three.js 唯一的数据来源 |
| **上下文腐烂** | 采集的上下文随时间/转手丢失原始性，被推断、摘要、改写逐步污染的现象 |

## 5. 用户与首要场景

- **首要用户假设（TBD-U1，未最终确定）**：高频参加黑客松/展会/投资活动的人（投资人、创业者、 BD）。
- **首个 Demo 场景（2026-08-03 升级为现场群体模式）**：黑客松/展会现场群体冷启动。一张合照 → AI 分割批量建档 → 每人自拍 + 自评一条特征 + 同伴互评 → 生成体素形象进入市集世界 → 破冰互动持续采集数据 → 多设备各自操纵 + 大屏全场视角演示。

## 7. MVP 1.0 需求 —— 人脸记忆闭环

**目标**：用户能明确感受到"原本会忘记的一次相遇，被完整记住了"。

### 功能需求

- **FR-1.1 相遇采集**：通过摄像头 + 麦克风录制一段现场交流（Demo 阶段手机摄像头即可，不追求眼镜）。输入：视频/音频/手动备注。输出：原始媒体文件，只增不改。
- **FR-1.2 人物与场景提取**：从录制内容中提取人脸照片、语音转写、人物自我介绍、场景画面。输出：结构化草稿，待用户确认。
- **FR-1.3 用户确认绑定**：人脸与身份由用户显式确认后才写入 Package（防错误绑定）。未确认的数据标记为"待确认"，不进入 Agent 上下文。
- **FR-1.4 Package 生成**：生成符合 CONTEXT-AND-MEMORY.md#schema 的人物资料包（事实层 + 空推断层）。
- **FR-1.5 人物模型生成**：为 Package 生成 MC 体素人物形象。正式路径为生成管线（照片 → AI 生成图片贴图 → 体素 GLB 组装，接口预留、MVP1 用 mock 跑通，见 ARCHITECTURE.md §5a）；管线打通前用现有体素占位（固定身体 + 默认贴图）。资料包内始终保留真实人脸照片。
- **FR-1.6 场景模块生成**：用固定模板（展位/桌位）+ 现场照片贴图生成相遇场景模块。
- **FR-1.7 个人世界浏览**：Three.js 世界中可走动查看自己认识的人和场景（沿用现有 EchoWorld 咖啡厅原型演进）。
- **FR-1.8 上下文恢复**：点击像素小人 → 展示资料包（真实人脸、相遇时间地点、谈话要点、现场照片）。这是 MVP1 的核心价值时刻。
- **FR-1.9 上下文找回**：主路径为"世界即入口"（世界中遇到并点开）与"系统主动浮现"（再次相见时系统认出并提示）；姓名/关键词/人脸检索仅作底层能力保留，不作为产品入口。（2026-08-03 调性修正：本产品不是工具型通讯录，用户不存在"拿照片来查库"的场景。）

### 非功能需求

- **NFR-1.1**：事实层数据只增不改，任何编辑都产生新版本而非覆盖。
- **NFR-1.2**：所有 UI 文案简体中文。
- **NFR-1.3**：MVP1 不做 Agent 自主交谈之外的任何"智能"承诺；展示的交流内容必须来自真实记录，不编造。

### 验收标准（MVP1 完成的定义）

1. 现场录制一段 1 分钟相遇，5 分钟内生成可浏览的像素小人 + 场景模块 + 资料包。
2. 关闭页面重开，资料包内容与原记录完全一致（事实层零损耗）。
3. 模拟"再次相见"：世界中点开该人，资料包完整呈现相遇上下文（检索仅作底层能力抽测，不作为用户路径验收）。
4. 新用户无需教学即可完成一次录入-查看闭环。

## 8. MVP 2.0 需求 —— 场景、互动与群体冷启动（2026-08-03 重设）

**前置条件**：MVP1 验收通过。
**目标**：从"一个人的世界"到"一群人可以现场一起玩的世界"。验证两个问题：场景能否承载互动？上下文产品如何从零启动？

> 原 MVP2 的 Agent 价值发现方向（原 FR-2.1~2.7：价值匹配、事件推送、微信行动建议）与第 9 章 MVP3 整体**暂缓**：相关内容依赖大模型分析与足够的上下文积累，当前阶段过虚，待 MVP2 数据后重议。编号保留，不重用。

### 功能需求

- **FR-2.8 场景语言**：点位交互——靠近热点（桌位/吧台/圆桌/摊位）出现 E/F 按键提示，坐下出情境菜单（喝咖啡/邀请人/发起会议）；交互全部按键化，不做复杂操作。原 FR-2.2 圆桌会议需求并入本条。
- **FR-2.9 世界播报**：场景内大屏滚动播报近期世界事件（谁认识了谁、发生了什么）；每日进入时的"晨报"摘要（昨日新相遇与事件）。
- **FR-2.10 市集场景**：室外主场景"市集"——一条可扩展的街，摊位模块（背景板可贴现场照片）；咖啡厅作为街上的一间室内小屋（熟人社交定位）；摊位/小屋遵循应用入口模块规范，后续应用可挂载。
- **FR-2.11 个人场域**：AI 根据个人素材生成特质空间（风格化、有隐喻，粗糙可用）；进入他者场域即访问交互的空间表达。**场域是推断层的视觉化产物**：必须标注为生成物、可随素材重算，不得与事实层场景模块混淆（P-3）。
- **FR-2.12 合照分割群体录入**：一张大合照 → AI 分割出每个人 → 批量建档（人脸 → 唯一 person_id）。
- **FR-2.13 第一印象互写**：入场流程中每人自评 1 条特征 + 每位同伴互评 1 条，进场即带 5–6 条特征（写入推断层，带来源与作者）。
- **FR-2.14 现场演示模式**：多设备各自操纵自己的形象 + 大屏全场视角（单机架构内实现；实时联机为远期方向，见 FR-3.6）。

### 验收标准

1. 现场 ≥5 人合照入场：10 分钟内全部生成形象与特征，世界可浏览。
2. 场景语言完整走通一次：点位交互 → 邀请 → 圆桌 → 播报屏可见该事件。
3. 破冰互动后数据回流，世界发生可见变化（新特征/新事件上屏）。

### 暂缓项（编号保留，MVP2 验收后重议）

- 原 FR-2.1 Agent 运行时（规则驱动调度）——保留为基础设施继续演进，不作为 MVP2 验收项。
- 原 FR-2.3 Agent 交互协议、FR-2.4 价值匹配、FR-2.5 事件推送、FR-2.6 微信行动建议、FR-2.7 反馈回路——暂缓（依赖大模型分析与上下文积累，当前过虚）。

## 10. 衡量指标

- MVP1：录入完成率、再次相见时的上下文恢复成功率、资料包查看频次。
- MVP2：现场入场完成率、人均特征条数、场景互动触发率、破冰后数据回流量。
- MVP3（暂缓）：跨网络匹配数、组织内知识复用次数——随 MVP3 重议。
- 北极星候选（TBD-M1）：**促成的真实行动数**（重新联系、引荐、合作），而非"记住人数"或"连接次数"。
