# EchoWorld 产品需求文档（PRD）

> 一句话：把现实世界中的每一次相遇，转化为一个可以长期存在、持续行动、与其他智能体交互的 3D 智能体，最终形成由真实关系冷启动的智能体关系网络。

## 1. 产品本质

我们做的不是 3D 游戏，也不是 AI 社交软件，而是一套基础设施：

> 将现实世界中的相遇，转化为一个持续演化的智能体关系网络。

- 一次现实相遇被封装成 **Package**（不是名片，不是聊天记录，而是完整的"认识事件"）。
- Package 生成 **Agent**，Agent 不住在列表里，而是**生活在一个世界里**：走动、访问、交谈、参加圆桌、产生新事件。
- 3D 不是包装，而是让人物、场景、关系、事件成为**可看见、可操作、可重新组织的对象**。

## 2. 设计原则（优先级从高到低，冲突时以上位原则为准）

### P-1 严防上下文腐烂
宁可闭环小，也要完整。**一个阶段的交互场景复杂度，不得超过当前已采集上下文的量能支撑的水平。** 有什么量的上下文，就做什么样的有用且有趣的交互；上下文不够的功能不做，而不是用编造的内容填充。

### P-2 从"人脸记忆"单闭环起步
第一个闭环只有一个任务：**把人脸和相遇第一现场忠实记录下来**，并在再次相见时可靠地恢复上下文。此闭环未验证前，不扩展其他场景。

### P-3 原始事实与模型推断彻底分离
- **事实层**（照片、录音、转写、时间地点）：只增不改，永远保留原始形态。
- **推断层**（标签、兴趣、匹配建议）：可随时重算，必须携带来源、置信度与生成时间，**永远不允许回写污染事实层**。
- 详见 CONTEXT-AND-MEMORY.md。

### P-4 核心单位是「人物 × 事件」，不是「人物」
底层至少两层对象：**人物资料包**（相遇事件 + 原始图片/语音上下文）与**像素小人**（Agent 的可视化形态）。一个人在不同事件中的面貌是不同的 package 条目，而不是被合并成一个静态档案。

### P-5 克制的游戏化
游戏化只模拟**本来就会发生的事情**：圆桌讨论、展会交谈、展位访问。不做打怪升级式的虚构玩法。游戏化的目的是驱动打开率、让网络可观赏、让上下文可浏览，而非娱乐本身。

### P-6 Per-person 低多边形模型 + 真实资料包的人物形象策略
每个真实的人由生成管线（照片 → AI 三视图 → Blender lowpoly GLB）产出**有脸的个性化模型**，目标是"看一眼能认出是谁"；资料包中同时保留真实人脸照片与第一现场。低多边形风格控制成本与恐怖谷风险。硬件输入打通前，临时使用无脸占位模型（同一几何按调色板换色），占位不是方向。

### P-7 主动式增量上下文捕获
系统不只被动记录，还要主动索取增量信息。典型路径：连接真实微信场景，给用户**具体的、可执行的微信操作建议**（如"可以问 A 是否在做教育项目"），用户执行后把新上下文带回系统。

### P-8 隐私权限是产品机制，不是事后补丁
人脸、声纹、对话内容的使用边界（仅自己 / 自己 agent 可用 / 组织内 / 本人同意公开）从第一行代码起就是数据模型的一部分。详见 CONTEXT-AND-MEMORY.md#权限圈层。

## 3. 我们不在做什么（边界）

- 不是纯粹的 3D 游戏；游戏只是表达和驱动机制。
- 不是 AI 宠物/陪伴产品；agent 来自真实人物与真实相遇。
- 不是人脸识别工具；识别只是输入环节。
- 不是静态通讯录/知识库；信息进入 agent 并持续行动。
- 不是纯线上陌生人匹配；从真实线下关系冷启动。
- 不是完全自治的社会模拟实验；目的是解决关系记忆、信息复用与价值连接。

## 4. 术语表

| 术语 | 定义 |
|---|---|
| **相遇事件 Encounter** | 一次现实中的认识过程，含时间、地点、场景、对话、双方行为 |
| **人物资料包 PersonPackage** | 从 Encounter 形成的结构化数据单元：人脸、声纹、身份、介绍、交流内容、兴趣需求、关系、后续事件。**产品的最基础数据单元** |
| **像素小人 / Agent** | Package 的可行动形态：在世界中移动、访问、讨论、交换授权信息、产生事件、向真人反馈 |
| **场景模块 SceneModule** | 「一个人 + 第一次认识他的场景」的组合（人物 + 展位/场景 + 上下文） |
| **个人关系世界 World** | 每个用户拥有的世界，生活着其认识的人的 Agent 与场景模块；早期形态为"集市/咖啡厅" |
| **智能体网络 Network** | 多个 Agent 交互形成的关系与价值匹配网络，产品长期最有价值的部分 |
| **世界快照 World Snapshot** | World Service 输出的世界状态序列化结果，Three.js 唯一的数据来源 |
| **上下文腐烂** | 采集的上下文随时间/转手丢失原始性，被推断、摘要、改写逐步污染的现象 |

## 5. 用户与首要场景

- **首要用户假设（TBD-U1，未最终确定）**：高频参加黑客松/展会/投资活动的人（投资人、创业者、 BD）。
- **首个 Demo 场景**：黑客松/展会。用户持摄像头走到展位前 → 拍下展位、产品、介绍者的人脸与声音、双方谈话 → 系统生成像素小人 + 展位模块 + Package → 出现在用户的 3D 集市中。

## 6. MVP 路线总览

| 阶段 | 验证的闭环 | 核心问题 |
|---|---|---|
| **MVP 1.0 人脸记忆** | 相遇采集 → Package → 像素小人/场景进世界 → 再次相见时恢复上下文 | 系统能否忠实记住"他是谁、在哪认识、聊了什么"？ |
| **MVP 2.0 Agent 互动** | Agent 访问/圆桌 → 大模型发现连接 → 推送真人 → 微信行动建议带回增量上下文 | 沉睡关系能否重新产生价值？ |
| **MVP 3.0 网络与组织** | 多用户网络接触 → 授权共享 → ToB 平台（客户知识/销售关系/资源连接） | 一个网络和另一个网络能否交互并匹配价值？ |

每个 MVP 的详细需求见下节；打勾制任务分解见 ROADMAP.md。

## 7. MVP 1.0 需求 —— 人脸记忆闭环

**目标**：用户能明确感受到"原本会忘记的一次相遇，被完整记住了"。

### 功能需求

- **FR-1.1 相遇采集**：通过摄像头 + 麦克风录制一段现场交流（Demo 阶段手机摄像头即可，不追求眼镜）。输入：视频/音频/手动备注。输出：原始媒体文件，只增不改。
- **FR-1.2 人物与场景提取**：从录制内容中提取人脸照片、语音转写、人物自我介绍、场景画面。输出：结构化草稿，待用户确认。
- **FR-1.3 用户确认绑定**：人脸与身份由用户显式确认后才写入 Package（防错误绑定）。未确认的数据标记为"待确认"，不进入 Agent 上下文。
- **FR-1.4 Package 生成**：生成符合 CONTEXT-AND-MEMORY.md#schema 的人物资料包（事实层 + 空推断层）。
- **FR-1.5 人物模型生成**：为 Package 生成低多边形人物形象。正式路径为生成管线（照片 → 三视图 → Blender GLB，接口预留、MVP1 用 mock 跑通，见 ARCHITECTURE.md §5a）；管线打通前用无脸占位模型按调色板换色。资料包内始终保留真实人脸照片。
- **FR-1.6 场景模块生成**：用固定模板（展位/桌位）+ 现场照片贴图生成相遇场景模块。
- **FR-1.7 个人世界浏览**：Three.js 世界中可走动查看自己认识的人和场景（沿用现有 EchoWorld 咖啡厅原型演进）。
- **FR-1.8 上下文恢复**：点击像素小人 → 展示资料包（真实人脸、相遇时间地点、谈话要点、现场照片）。这是 MVP1 的核心价值时刻。
- **FR-1.9 上下文找回**：主路径为"世界即入口"（世界中遇到并点开）与"系统主动浮现"（再次相见时系统认出并提示）；姓名/关键词/人脸检索仅作底层能力保留，不作为产品入口。（2026-08-03 调性修正：本产品不是工具型通讯录，用户不存在"拿照片来查库"的场景。）

### 非功能需求

- **NFR-1.1**：事实层数据只增不改，任何编辑都产生新版本而非覆盖。
- **NFR-1.2**：所有 UI 文案简体中文。
- **NFR-1.3**：MVP1 不做 Agent 自主交谈之外的任何"智能"承诺；展示的交流内容必须来自真实记录，不编造。

### 验收标准（MVP1 完成的定义）

1. 现场录制一段 1 分钟相遇，5 分钟内生成可浏览的像素小人 + 场景模块 + 资料包。
2. 关闭页面重开，资料包内容与原记录完全一致（事实层零损耗）。
3. 模拟"再次相见"：世界中点开该人，资料包完整呈现相遇上下文（检索仅作底层能力抽测，不作为用户路径验收）。
4. 新用户无需教学即可完成一次录入-查看闭环。

## 8. MVP 2.0 需求 —— Agent 互动与价值发现

**前置条件**：MVP1 验收通过，且人均 Package 数 ≥ 10（上下文量足够，遵守 P-1）。

### 功能需求

- **FR-2.1 Agent 运行时**：规则驱动为主（每天随机走动、访问 N 个 Agent、定期圆桌讨论），平衡随机与目的性。Agent 行为只能读取授权范围内的上下文（P-8）。
- **FR-2.2 圆桌会议**：用户可对中央圆桌发起会议，邀请若干 Agent 围绕主题讨论（真实场景的模拟，符合 P-5）。
- **FR-2.3 Agent 交互协议**：Agent 间交换结构化信息（我是谁/我有什么/我需要什么/我认识谁/授权范围），不是自由聊天。
- **FR-2.4 价值匹配**：大模型分析互动结果，判断共同点、合作可能、引荐价值。匹配结论属于推断层，必须带置信度与依据。
- **FR-2.5 事件推送**：只推送"值得真人行动"的事件（默认每个价值事件需通过阈值过滤）。推送样例："你认识的 A 正在寻找教育项目，你认识的 B 可能符合。"
- **FR-2.6 微信行动建议（P-7）**：推送附带具体可执行的微信操作建议；用户执行后可一键回填结果，形成增量上下文。
- **FR-2.7 用户反馈回路**：用户对推送做"有用/无用"反馈，反馈写入推断层用于调优阈值，**不进入事实层**。

### 验收标准

1. 10 个 Package 的世界运行 24 小时（加速模拟可接受），产出 ≥ 1 条用户判定"有用"的连接建议。
2. 推送噪声可控：无用推送率 < 50%（初期目标，逐步收紧）。
3. 微信建议 → 用户执行 → 增量上下文回填的闭环可完整走通一次。

## 9. MVP 3.0 需求 —— 网络与组织

### 功能需求

- **FR-3.1 本人确认与授权**：被记录者可注册并确认/修正自己的 Package，解锁信息共享级别。
- **FR-3.2 网络接触**：两个用户建立真实关系后，双方世界的授权部分开始互联（A 的网络与 B 的网络发生接触）。
- **FR-3.3 组织空间**：企业/活动方可建立组织世界，成员的客户知识与关系在授权范围内共享（AI 销售知识库的 3D 化）。
- **FR-3.4 活动模式**：黑客松/展会组织方批量入场，现场相遇实时生成 Package 与展位模块。
- **FR-3.5 平台 API**：Package/世界快照/匹配事件的对外 API，供第三方集成。

### 验收标准（TBD，随 2.0 数据细化）

1. 两个真实用户的网络互联后，产生至少一条跨网络的有效匹配。
2. 组织空间内权限隔离通过安全走查（未授权信息零泄漏）。

## 10. 衡量指标

- MVP1：录入完成率、再次相见时的上下文恢复成功率、资料包查看频次。
- MVP2：推送有用率、微信建议采纳率、增量上下文回填量。
- MVP3：跨网络匹配数、组织内知识复用次数。
- 北极星候选（TBD-M1）：**促成的真实行动数**（重新联系、引荐、合作），而非"记住人数"或"连接次数"。
