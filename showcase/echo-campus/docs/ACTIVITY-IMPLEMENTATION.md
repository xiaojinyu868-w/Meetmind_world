# Echo Campus 活动实施与技术对接清单

**版本**：v0.2 · 2026-09-18 · 活动花园展示版
**适用项目**：两天、约 1,000 位来宾的线下活动；白色园区 3D 世界、手环 NFC 入场、来宾风格化分身、打卡点与线上相遇。
**文档用途**：把活动方、阿里巴巴/支付宝技术方与 Echo Campus 技术方需要确认的输入、实施步骤和验收口径放在同一张清单里。本文件是实施底稿，不代替支付宝正式接口文档、隐私协议或最终报价。

## 1. 我们要交付的现场闭环

来宾佩戴按身份类别区分的手环，在手机上轻触 NFC 后打开活动专属 HTTPS 入口；若手机或 NFC 路由不支持，则使用同一入口的二维码或短链接。来宾只填写愿意公开的资料，领取一个风格化数字分身并进入活动世界。大屏展示人数、空间和已确认的关系；手机可以查看名片、发现供需互补的伙伴并发起相遇。对方确认后，连接才进入公共世界。

打卡点使用同一身份凭据完成一次性签到，返回积分与点位反馈。积分规则、奖品和是否公开排行榜由活动方决定。现场网络或 NFC 临时不可用时，应保留二维码/短链接和人工引导路径；当前演示服务没有离线补传机制，这一项需在生产联调中确定。

活动结束后，活动方可以保留经同意的公开名片和已确认连接，作为后续联系入口；保存期限、导出范围和删除规则必须在活动前由活动方书面确认。

## 4. NFC / 支付宝技术对接

### 4.1 目前已经具备的网页侧契约

- Echo Campus 提供 HTTPS 入场页和公开资料领取流程，可由 NFC 标签、二维码或短链接打开。
- 当前公开入口是演示模式，允许创建虚构身份；正式活动需要活动方凭据或支付宝侧已验证的活动身份。
- 领取后，浏览器本地保留短期会话 token；服务端只保存 token 的 hash，不把 token 放在 URL。
- 双方确认和打卡写入均应通过 HTTPS API；WebSocket 只用于只读状态广播，不能从浏览器直接改写活动状态。

### 4.2 待与支付宝/阿里技术方确定的适配层

支付宝侧的具体 NFC 形态可能是“碰一下打开链接”、支付宝小程序/活动页路由，或带签名的卡片凭据。不能仅凭“支持 NFC”推断接口已经确定。对接时需要拿到正式文档和沙箱参数，至少确认：

1. 触碰后打开的目标 URI、是否必须进入支付宝 App、未安装 App 时的降级页。
2. 回传字段：手环 UID/卡号、活动 ID、点位 ID、时间戳、随机数、签名算法和签名校验公钥。
3. 身份映射：UID 如何对应活动方的 attendeeId；一个 UID 是否只能绑定一次；补发、挂失、换卡如何处理。
4. 打卡回调：是每个点位独立回调，还是统一网页确认；重复触碰返回什么；是否有回调重试和幂等键。
5. 沙箱/生产域名、HTTPS 证书、回调白名单、服务限流、日志字段和故障联系人。
6. 支付宝侧是否承担实名或报名核验；Echo Campus 只接收哪一组最小字段。

建议建立一个独立的 `NFC/Alipay Adapter`：验证签名和活动范围，完成 UID → 活动身份映射，再调用 Echo Campus 的领取或签到服务。浏览器永远不持有支付宝密钥，也不直接相信手环上可复制的明文编号。正式接口到位前，可用二维码短链接跑通同一网页闭环，不把演示入口描述成已完成硬件验收。

### 4.3 两天活动的降级路径

1. **首选**：NFC/支付宝触碰 → 活动页 → 领取/签到。
2. **同页替代**：二维码或短链接 → 同一活动页；保留手环颜色识别。
3. **现场协助**：签到台按活动方名单补发/重绑凭据；不在公共页面输入激活码。
4. **服务异常**：现场大屏显示最近一次已同步快照，主持人口播引导二维码；技术值守记录未上报的 UID/点位，恢复后按受控重放规则补记。

第 4 步涉及离线补记，当前服务尚未实现自动队列；是否允许人工补记、由谁审批、补记时间窗口和审计格式必须提前定稿。

### 5.1 可直接讨论的点位草案

### 5.2 生产版还需补上的规则

- 点位是否必须由 NFC 触碰触发，还是允许二维码/人工备用。
- “平台共创”需要填写什么最小内容，是否展示给合作方。
- 奖品档位、领取时机、同分排序和并列处理。
- 迟到补签、手环更换、工作人员账号、设备离线时的补记权限。
- 是否显示个人积分、排行榜、点位人数和大屏实时统计；默认建议只显示汇总人数，避免暴露个人轨迹。
- 活动方指定一名积分规则负责人，所有规则在 T-7 冻结。

## 6. 3D 场景素材、转换与预览

### 6.1 素材清单

活动方/场地方提供以下资料，优先提供原始建筑文件和贴图，而不是只给一张效果图：

- 已收到并转换三份建筑来源：`20231226_T1-3塔楼调整.skp`、`0801-T6雨棚模型-2017版本.skp`、`0831 Podium.3dm`，当前网页各有独立 GLB。请补充缺失位图贴图、外链、授权以及两种 AB 的实际版本/地块说明；有更新文件时再做差异审计，不需为当前展示重复提交已收到的文件。
- 若存在，提供 3D Max/FBX/CAD/BIM 原始文件、建筑总平面、层高和单位说明。
- 建筑至少 4 个方向的照片/渲染图，入口、主庭院、标志性建筑、道路和水面需单独说明。
- 可用于线上活动的 Logo、字体、材质、贴图及第三方资产授权证明。
- 场地入口、主舞台/大屏位置、打卡点位置、可行走区域和不希望展示的区域。
- 活动方确认的世界名称、镜头偏好、主色与夜间/白天氛围。

当前网页导入器接受 GLB/GLTF 或 Marble 的 SPZ/PLY/SPLAT，并允许调模型变换、地面、边界、锚点、镜头和碰撞。模型文件和 JSON 配置可以分开托管；本地导入只影响当前浏览器，多端共用必须托管到 HTTPS 并使用共享 `sceneManifest`。SPZ 画面不自动生成楼梯、坡道和多层碰撞，正式场景仍需人工配置活动平面和碰撞壳。

### 6.2 建议转换流程

```text
SU/3D Max/CAD/BIM
→ 资产授权与外链盘点
→ 删除不展示的楼层/室内细节
→ 单位、坐标、入口和地面校准
→ 合并材质、压缩贴图、减面与 LOD
→ 自包含 GLB（或授权的 Marble SPZ）
→ Echo Campus 导入
→ 桌面、手机、大屏与现场网测
```

当前三份场地已分别转换并验证，保持独立切换；在实际版本和地块对应关系确认前，不将两种 AB 与 C 擅自合成总场地。后续可按入口区、主活动区和远景区拆分或分段加载。作为首轮工程目标，可先控制自包含 GLB 在约 80 MB 以内、可见三角形约 150 万以内、贴图以 2K 为主；这是性能目标而非对原始文件的承诺，需根据实际 SU 内容和目标手机实测后调整。若最终 Marble 导出更适合 SPZ，应记录点数、显存/内存、首屏时间和手机表现，不用测试 SPZ 推断真实文件已通过。

### 6.3 场景交付验收

- 远景、入口、庭院和鸟瞰四个镜头构图成立。
- 入口与人物出生点落在同一地面，人物不漂浮、不埋入模型。
- 至少为预期人数提供互不重叠的锚点；舞台、展台、楼梯、河带等设置阻挡或禁行区。
- 浏览器刷新、切换场景、打开大屏模式均能恢复同一活动身份和已确认关系。
- 目标手机完成首屏时间、内存、帧率与连续运行检查；桌面 1440×900 的检查不能替代实机验收。
- 发生加载失败时保留上一套可用场景，并能通过二维码/链接回到稳定版本。

## 7. 实施阶段、人员与成本框架

以下保留前期工程量级供合作讨论，不是最终报价，也不是当前剩余工作量承诺。三份建筑转换与活动花园演示已完成；正式报价需扣除已完成部分，并按最终模型、支付宝接口、活动规则和现场验收范围重新估算。外部硬件、NFC 手环、支付宝平台费用、云资源、差旅和现场搭建另计。

| 阶段 | 主要工作 | 估计周期 | 估计工作量 |
| --- | --- | ---: | ---: |
| 0. 需求与资产审计 | 活动流程、字段、类别、点位、模型授权、支付宝沙箱资料 | 1–2 个工作日 | 2–4 人日 |
| 1. 场景首版 | SU/GLB/SPZ 清理、转换、地面/镜头/锚点、视觉验收 | 3–7 个工作日 | 5–10 人日 |
| 2. 活动功能适配 | 类别与手环色、弱字段、点位/积分、Adapter、现场面板 | 5–8 个工作日 | 8–15 人日 |
| 3. 双端与容量验收 | NFC 实机、手机/大屏、并发、恢复、日志与安全检查 | 3–5 个工作日 | 5–8 人日 |
| 4. 现场准备 | 彩排、冻结版本、值守手册、备份入口与两日支持 | 活动前 1–2 日 + 活动 2 日 | 6–10 人日 |

粗略预算可以按三档讨论：

- **场景适配展示版**：约 5–10 人日，人民币 **1.5–3 万**；适合先把 C 地块或一套白色建筑做成可浏览首版。
- **活动 MVP**：约 15–25 人日，人民币 **5–9 万**；含一套定制场景、网页闭环、类别/点位接口适配和基础验收，不含硬件及平台费用。
- **两天千人生产版**：约 25–40 人日，人民币 **10–18 万**；含容量与现场演练、值守与故障预案。最终价格由模型复杂度、支付宝接口工作量、现场人员数量和是否需要活动后数据服务决定。

已完成本轮实际建筑文件的转换审计；报价前仍需确认素材授权、补充贴图及正式接口文档。如果新增原始文件带大量室内细节、外链贴图或授权限制，应以差异审计结果重估。

### 8.2 建议服务目标（待合同确认）

| 级别 | 事件 | 响应目标 | 处理目标 |
| --- | --- | ---: | ---: |
| P0 | 活动入口、API 或大屏整体不可用 | 5 分钟内确认 | 30 分钟内恢复或切换二维码/稳定版本 |

## 9. 隐私、安全与数据边界

- **最小化**：全部资料选填；不填写职业、供给、需求或联系方式也能以临时访客身份进入。未提供的供需不用于推断推荐。
- **分层同意**：活动公开展示、供需推荐、公开联系方式应分开说明；未同意的资料不进入公共 DTO。
- **身份隔离**：演示入口的身份是 synthetic，不等于实名；生产 UID/报名身份映射由活动方或支付宝适配层完成。
- **凭据保护**：不在 URL、二维码、截图或公共日志中暴露激活码、session token、支付宝密钥；服务端只保存 token hash 和必要的活动记录。
- **访问控制**：待确认相遇只对双方可见；只有确认后的关系才进入公共世界；工作人员补记、导出和删除操作应有独立权限与日志。
- **数据留存**：建议活动结束后按活动方确认的期限保留（例如 30/90 天），到期删除联系人、会话和可识别数据；统计汇总可单独保留。最终期限、导出人、删除人和审计记录由活动方书面确认。
- **第三方合规**：支付宝、手环厂商、云服务与技术方各自处理什么字段，应在活动隐私说明和合作协议中列明。
- **安全边界**：当前系统不保存照片、声音或 embedding，不宣称真人数字人；若未来接入照片/声音/LLM，应另做授权、保存和供应商安全评估。

## 10. 联调与验收用例

### P0：必须通过

- [ ] NFC/支付宝沙箱触碰后进入正确活动页；未安装 App 或 NFC 失败时二维码/短链可用。
- [ ] 来宾选择类别后手环色、分身色和名片类别一致；错误类别无法提交。
- [ ] 全部资料留空、主动同意后可以进入；临时昵称与来宾角色正常显示。供需全空不产生推荐；更新资料时同意不预勾选。
- [ ] 联系方式默认不公开；关闭公开开关的来宾在公共接口和大屏不出现联系方式。
- [ ] 分身出现在园区；名片、推荐理由、发起请求、对方确认和大屏同步闭环通过。
- [ ] 每个点位同一来宾重复触碰不重复计分；无效点位、他人凭据和越权确认被拒绝。
- [ ] 场景加载失败保留稳定版本；GLB/SPZ 的地面、边界、出生点和四个镜头均通过人工走查。

### P1：生产前必须通过

- [ ] 1,000 条模拟/真实活动身份可导入；峰值并发、读写、WebSocket 连接和数据文件增长完成压测。
- [ ] 至少两种 iOS/Android 真机、支付宝入口、二维码入口、低速网络和断网恢复完成走查。
- [ ] 大屏连续运行两天的浏览器内存、GPU、自动刷新和断线重连通过；有稳定版本和静态二维码备份。
- [ ] 日志不含 token、激活码或联系方式；导出文件按活动方授权范围生成。
- [ ] 现场值守、联系人、P0/P1 降级路径和人工补记审批完成彩排。

## 11. 只需要活动方确认/提供的事项

技术方可以先按当前原型继续准备；以下事项不能由技术方替活动方决定，确认后才能冻结生产版本：

1. 活动正式名称、副标题、日期、地点、入口域名和大屏文案。
2. 参与类别最终列表、中文名称、手环颜色/图标、数量和补发规则。
3. 阿里巴巴/支付宝对接负责人、正式 NFC 形态、沙箱/生产文档、回调签名方式和身份映射责任人。
4. 三份已收到模型的版本/地块对应、最终采用和组合方式、单位/层高/入口说明、缺失贴图与第三方授权；如原文件已更新，再提供新版 3D/CAD 文件。
5. 点位清单、合作方名称、每点分值、奖励、排行榜和反作弊规则。
6. 公开字段与同意文案；联系方式、活动后联系入口、数据留存/删除期限和导出范围。
7. 是否需要实名核验、报名名单同步、工作人员/志愿者特殊权限；技术方只接收的最小字段。
8. 目标设备清单（iOS/Android 型号、支付宝版本）、大屏数量/分辨率、现场网络、备用网络和电源。
9. 预算档位、付款节点、场景与活动功能的最终范围；是否需要 T-1/T+1 现场支持。
10. 活动方现场总负责人、支付宝技术联系人、网络联系人和隐私/法务联系人；每位提供可用电话和升级顺序。
